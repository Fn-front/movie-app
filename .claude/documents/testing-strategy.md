# テスト戦略 — テスティングトロフィーモデル

## 概要

本プロジェクトでは **テスティングトロフィー** モデルを採用する。ピラミッド型（単体テスト最多）ではなく、**結合テストを最も厚く**し、ユーザーの実際の使い方に近いテストを重視する。

```
        ▲  E2E（少数・クリティカルフローのみ）
       ▲▲▲
      ▲▲▲▲▲  結合テスト（最も厚い層）
     ▲▲▲▲▲▲▲
    ▲▲▲▲▲▲▲▲▲  単体テスト（純粋ロジックのみ）
   ━━━━━━━━━━━  静的解析（TypeScript + ESLint）
```

## 各テストレイヤーの役割と境界

### 1. 静的解析（TypeScript + ESLint）

**ツール**: TypeScript strict mode, ESLint（カスタムルール含む）

**検証対象**:
- 型エラー・型の整合性
- コード品質・スタイル一貫性
- useEffect内非同期処理のクリーンアップ（カスタムルール）

**このレイヤーで解決すべき問題**:
- 「実行せずに防げるバグ」はすべて静的解析で捕捉する
- 型定義が正確であれば、テストで型の確認は不要

### 2. 単体テスト（Jest）

**ツール**: Jest

**検証対象**:
- 純粋関数（入力→出力が決まっているもの）
- ユーティリティ関数（date, string, image, validation, error）
- zodスキーマのバリデーションロジック
- 定数・設定値の正当性
- Zustandストアのロジック

**判断基準**: 「外部依存なし・UIなし・副作用なし」なら単体テスト

**このレイヤーでやらないこと**:
- コンポーネントのレンダリング確認
- API呼び出しを伴うロジック
- DOMとのインタラクション

### 3. 結合テスト（Jest + React Testing Library）

**ツール**: Jest, React Testing Library, @testing-library/user-event

**検証対象**:
- コンポーネントの振る舞い（レンダリング・ユーザー操作・状態変化）
- カスタムフック（renderHook + モックされた依存関係）
- API Route（リクエスト→レスポンスの検証）
- フォームのバリデーション・送信フロー
- コンポーネント間の連携（親子コンポーネントの統合）
- モーダルの開閉・Toast表示などのUI状態

**判断基準**: 「ユーザーがUIを通じて体験する振る舞い」は結合テスト

**テスト方針**:
- 実装詳細（state値・内部メソッド）ではなく、ユーザーが見る結果をテスト
- アクセシビリティ優先クエリ（getByRole > getByLabelText > getByText）
- 外部APIはモックし、コンポーネント内部のロジックを検証

### 4. E2Eテスト（Playwright）

**ツール**: Playwright

**検証対象**: クリティカルユーザージャーニーのみ

**対象とするフロー（例）**:
- 認証フロー（ログイン→認証済みページアクセス→ログアウト）
- 映画一覧表示→詳細モーダル表示
- ウォッチリスト追加→サイドバー反映→削除
- 未認証アクセス→リダイレクト

**対象としないもの**:
- 個々のUIコンポーネントの表示確認（結合テストで検証）
- バリデーションエラーの網羅的な確認（結合テストで検証）
- 個別のaria属性の確認（結合テストで検証）

## 「何をどのレイヤーで検証すべきか」判断フローチャート

```
対象は純粋関数か？（副作用なし・UIなし）
  → YES → 単体テスト
  → NO ↓

UIコンポーネントの振る舞いか？
  → YES → 結合テスト（Jest + RTL）
  → NO ↓

API Routeのリクエスト/レスポンスか？
  → YES → 結合テスト（Jest）
  → NO ↓

複数ページをまたぐユーザーフローか？
  → YES → そのフローはビジネス上クリティカルか？
    → YES → E2Eテスト
    → NO → 結合テストで各ページを個別に検証
```

## E2E設計思想

### 対象範囲

E2Eは **クリティカルユーザージャーニー** に限定する。「壊れたらサービスが使えない」レベルのフローのみ。

### 安定性ルール

| ルール | 説明 |
|---|---|
| Web-Firstアサーション必須 | `expect(locator).toBeVisible()` 等、Playwright組み込みの自動リトライアサーションを使用 |
| `waitForTimeout` 禁止 | 固定時間待機はフレークテストの原因。`waitFor` や `expect` の自動リトライで代替 |
| ロード完了待機 | ページ遷移後は要素の表示を `waitFor` で確認してからアサーション |
| タイムアウト設定 | テスト全体: 30s、アサーション: 10s、データ依存の待機: 最大30s |

### データ依存テストの扱い

- **外部API依存**（TMDb等）: データの有無で分岐する soft assertion を使用
  ```typescript
  // OK: データがある場合のみ検証
  const hasCast = await dialog.getByText('キャスト').isVisible().catch(() => false);
  if (hasCast) { await expect(castSection).toBeVisible(); }
  ```
- **自アプリのデータ変更**: 追加→検証→削除で元に戻す（クリーンアップ必須）
- **DB汚染を避けられないテスト**: `test.skip` で保護（例: 新規ユーザー登録）

### 共通ヘルパー管理

- 2つ以上のspecファイルで使うロケータ・操作は `e2e/helpers/` に集約
- 各specファイルからimportして使用
- specファイル内にローカルヘルパーを定義する場合、そのファイル内でしか使わないものに限定

## テストの安定性ルール（全レイヤー共通）

### フレーク対策

- **非決定的な値に依存しない**: Date.now()、Math.random() 等はモックする
- **テスト間の独立性**: 各テストは他のテストの実行結果に依存しない
- **クリーンアップ**: afterEach/afterAll でモック・状態をリセット

### 待機戦略

| レイヤー | 待機方法 |
|---|---|
| 単体テスト | 不要（同期処理）、async の場合は `await` |
| 結合テスト | `waitFor`, `findBy*`（RTLの自動リトライ） |
| E2E | Playwrightの Web-First アサーション（自動リトライ） |

### カバレッジ目標

- 全指標（Statements, Branches, Functions, Lines）で **80%以上**
- カバレッジは結合テスト + 単体テストの合算で達成
- E2Eテストはカバレッジ計測の対象外
